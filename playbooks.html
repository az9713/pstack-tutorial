Playbooks: copy, adapt, paste

A playbook is a written list of steps for one kind of job. pstack has 23 of them. You do not call a playbook by name. You type /poteto-mode and describe the job. /poteto-mode reads your words, picks the playbook that fits, copies its steps into a todo list, and works through them.

This page is a reference for all 23. Each page has the same parts, so you can find what you need fast.

How to use a prompt from this page

  1. Pick the playbook that matches your job. Use the table below.
  2. Copy a prompt from its Copy and adapt section.
  3. Replace each <placeholder> with your own words.
  4. Keep the phrases that name the job, such as "repro first" or "don't change any code yet". The router uses them to pick the playbook.
  5. Paste it into a Cursor chat.

The filled-in examples show the level of detail that works. A prompt does not need to be long.

Some playbooks have no published trigger phrase. For those, the prompts use wording we chose from the playbook text. If /poteto-mode picks the wrong playbook, name the one you want in the prompt, for example "use the babysit playbook".

What a good prompt carries

A good prompt has up to five parts. Each part fits in one sentence.

Part Example
The goal "the export drops its last row"
The done check "done means the 60k-row fixture exports every row"
The proof "show me the row counts before and after"
What you know "failing job id is 4812"
The real constraints "repro first", "don't change any code yet", "let me review before you proceed"

Do not list steps or skills in your prompt. The playbook already holds them in the right order.

Three habits that make every playbook work better

  • Say "new task" when you change subject. This tells /poteto-mode to choose a fresh playbook instead of continuing the last one.
  • Keep the mode on. Pick /poteto-mode from the / menu and press Option+Enter (Mac) or Alt+Enter (Windows). It becomes a Custom Mode that stays in context on every turn. Then short follow-ups such as "continue" are enough.
  • Ask for evidence you can inspect. A video, a screenshot, a command output, or a before-and-after number. A reply that says "done" without evidence is a warning sign.

Investigation

Use it when. You have a question about how something works, why it was built that way, or whether to pick option A or B, and you want an answer without any code change.

In plain words. An investigation is read-only. The agent reads the code and the history and writes a cited explanation. A cited explanation points at the files and facts that back each claim, so you can check them. The playbook uses the how skill to explain mechanics and the why skill to explain motivation. If your question is a choice between options, you get a recommendation with a trade-offs table instead.

What it does.

  1. Routes the question through the how skill. For questions about motivation, it also routes through the why skill.
  2. Writes one line for the throughput checkpoint, which reads throughput checkpoint: n/a, read-only investigation.
  3. Writes the answer in the how shape. The sections are Overview, Key Concepts, How It Works, Where Things Live and Gotchas.
  4. Writes a recommendation with a trade-offs table instead, if the question is a decision between alternatives.
  5. Applies the unslop skill to the reply.
  6. Opens no PR, runs no babysit, and skips architect. If the findings point to a code change, it hands back to you, and the change becomes a new Bug fix or Feature task.

What you get back. The investigation output itself. For an "are we sure?" question, the reply includes the agent's real judgment with reasons. The agent pushes back if your premise is wrong.

Runtime Forensics

Use it when. Something is going wrong in a running program, such as a memory leak, a CPU spin while idle, or a visual glitch, and you want the cause before any fix.

In plain words. Forensics means finding the cause from evidence. Here the agent attaches to the live process and measures it, instead of guessing from the source. It captures a real artifact, such as a CPU profile or a heap snapshot, and reduces it to the one finding that explains the symptom. Then it tests that finding on the running process before it believes it. The deliverable is a diagnosis, not a fix.

What it does.

  1. Captures the live signal on the matching surface through the control skill. A spinning process gets a CPU profile, a leak gets a heap snapshot, and a visual glitch gets a CDP trace. CDP is the Chrome DevTools Protocol.
  2. Reduces the artifact to the smoking gun. Examples are the function on the hot path, the retainer chain from the leaked object to a GC root, or the loop that fires without input.
  3. Parses large artifacts in a subagent, following the guard-the-context-window principle skill. The main thread keeps only the reduced finding.
  4. Proves the mechanism. It injects instrumentation through CDP eval on the running process, or hotfixes the live code without reloading, to confirm the hypothesis cheaply.
  5. Maps the finding back to source, meaning the file, the symbol and the line that allocates or schedules.
  6. Writes one line for the throughput checkpoint, which reads throughput checkpoint: n/a, read-only forensics.

What you get back. The signal captured, the reduced finding, how the agent proved the mechanism, the source location and the artifact paths. There is no fix unless you ask for one.

Trace Forensics

Use it when. You already have a captured profiling file, such as a cpuprofile, a trace, a spindump or a heap snapshot, and you want to know what it says about the cause.

In plain words. A trace is a recorded timeline of a program run. In this playbook the capture is fixed data, so the agent reads it and does not run the program again. It loads the file into a sqlite database, which is a small file-based database you can query with SQL. Then it asks questions of the data until the cause shows up. The deliverable is a diagnosis, not a fix.

What it does.

  1. Identifies the format and loads it with the right tool. A parser for cpuprofile and .json.gz, a text editor for a spindump, heap tooling for a heapsnapshot.
  2. Parses large artifacts in a subagent, following the principle-guard-the-context-window skill. The main thread keeps only the reduced finding.
  3. Dumps the trace or heap snapshot into sqlite, with one row per sample, frame or node. It gets to a queryable shape before it reads.
  4. Narrows to the cause. It queries for the frames that hold the most time and walks the call tree to the hot path. For a leak, it follows the retainer chain to a GC root. For a spindump, it finds the thread stuck on-CPU or blocked, and its wait reason.
  5. Attributes the hot frame to a file, symbol and line through the artifact's own symbols. A frame with no source mapping is not a diagnosis yet. The agent resolves the symbols or says the artifact does not carry them.
  6. Diffs a paired before and after capture if one exists. Without a pair, it marks the finding as the strongest hypothesis the artifact supports, not a confirmed cause.
  7. Hands back a cited diagnosis with the throughput checkpoint line throughput checkpoint: n/a, read-only forensics.

What you get back. The artifact and its format, the reduced finding, the source location, the artifact paths, and whether a paired capture confirmed it.

Bug Fix

Use it when. You have a reported defect and you want it reproduced, traced to its root cause, and fixed with proof that it is gone.

In plain words. The agent runs the program itself and makes the bug happen before it touches any code. Then it narrows down the cause by ruling out candidate explanations one at a time, using runtime evidence. It ships only the smallest change that the evidence justifies. A guess that "might help" does not ship. The fix is checked on the same surface where the bug was first seen, so a passing unit test alone does not count.

What it does.

  1. Reproduces the bug itself on the matching surface through the control skill. It asks you only when it can state a specific reason the control surface cannot reach the target.
  2. Binary-searches the cause. A binary search splits the possible causes in half each time. It forms candidate hypotheses, seeds them with how and why (for regression history), and rules them out with runtime evidence until one survives. It can use Cursor's /loop command for a long hunt.
  3. Plans the fix. If the fix crosses a function boundary, it runs architect first. It delegates the implementation to a subagent with a specific scope.
  4. Verifies on the same surface. The original repro must now pass. A result of "inconclusive" or a check on the wrong surface is not a pass, and the agent flags it.
  5. Stages the commits so the failing repro lands before the fix in git history. When the bug has a cheap local test, it follows the tdd skill for the failing-test-first order.
  6. Runs the Opening a PR playbook.

What you get back. What was broken, the root cause, the fix, and how it was verified. The reply pastes the failing and then passing repro output verbatim.

  • A good habit is to name the surface in your prompt, for example the browser page or the command, so the agent drives the right one.

Perf Issue

Use it when. Something is measurably slow and you want it traced, fixed, and shown faster with before and after numbers.

In plain words. The agent measures first and fixes second. It captures a baseline, which is the starting measurement, and it checks that the measurement is trustworthy. Then it tries ideas in a fixed order from cheapest to most expensive, called the performance mantras. The cheapest idea is to not do the work at all. It stops at the first idea that meets the target and proves the result with a second measurement.

What it does.

  1. Captures a baseline trace through the matching control skill. It checks the baseline, and each later number, with the benchmark-checklist skill.
  2. Grounds hypotheses with how. It does not claim a performance ceiling without running it first.
  3. Tries the performance mantras in order, cheapest first. They are don't do it, do it but don't do it again, do it less, do it later, do it when they're not looking, do it concurrently, and do it cheaper. When an earlier mantra meets the target, it stops.
  4. Plans the fix from the trace. If the fix crosses a function boundary, it runs architect first. It delegates the implementation to a subagent, reviews the diff, and captures a post-fix trace. It verifies each attempt before the next, following sequence-verifiable-units.
  5. Parses and compares the artifacts, for example JSON into sqlite and a diff. A result of "inconclusive" or a check on the wrong surface is not a pass, and the agent flags it.
  6. Cites the measurement in the PR, then runs the Opening a PR playbook.

What you get back. The baseline number, the post-fix number, the delta and the artifact path.

  • This is a one-off fix. For sustained improvement against a metric, use the Hillclimb playbook.
  • If you want the cause only and no fix, use Runtime forensics or Trace forensics.

Hillclimb

Use it when. You want to improve one measurable number step by step toward a target, and a single fix is not enough.

In plain words. Hillclimbing is a loop. The agent changes one thing, measures, and keeps the change only if the number improves past noise and the tests stay green. Otherwise it reverts the change fully. Before the loop starts, the agent builds one repeatable measurement command and freezes it, so every attempt is judged the same way. It writes every attempt to a decision log, so you can see what was tried and why it was kept or dropped.

What it does.

  1. Grounds the workload with the how skill. It picks a case that reproduces your complaint, then fixes one metric, the direction that counts as better, and a stop predicate. The predicate pairs a target with a minimum number of attempts, for example "at least 50% better than baseline and at least 10 iterations".
  2. Builds the measurement harness, proves it can tell cases apart, and freezes it. It vets the harness with benchmark-checklist. It uses a median of N runs, and it records the baseline and a green run of the regression gate, which is the set of tests that must keep passing.
  3. Opens a decision log with the show-me-your-work skill. It is a decision.tsv with one row per attempt, kept out of the tree.
  4. Grounds each hypothesis in a specific mechanism. For a performance metric, it orders hypotheses by the performance mantras from the Perf issue playbook.
  5. Loops one hypothesis at a time. A subagent makes the change. The agent measures before and after, runs the regression gate, keeps a change only if the metric moves past noise and the gate stays green, and otherwise reverts it in full. It makes one commit per accepted fix and logs every row.
  6. Pushes past the first plateau by pivoting category, combining near-misses, re-reading the source, or trying something more radical. Correctness and simplicity outrank the number.
  7. Stops when the predicate is met, or when the remaining ideas are marginal.
  8. Runs the Opening a PR playbook with the accepted commits stacked in the order they landed.

What you get back. The metric and target, the baseline and final values with the percent change, the iterations run (kept versus reverted), one line per accepted fix, the decision.tsv path, and the best idea to try next.

Feature

Use it when. You want new or changed behavior in your code, such as a new flag, a new page, or a new export option.

In plain words. The agent acts as the lead designer. It studies the code, explores designs, and then hands the actual code-writing to a subagent (a helper agent that works on a narrow job). It names the data shape first, such as a table or a state machine, so the helper does not invent structure on the fly. A review and a check on the real running surface come before anything ships. The playbook works this way so the agent that designs also reviews, which catches mistakes the writer would miss.

What it does.

  1. Runs how over the part of the code the feature touches.
  2. Runs architect to explore design options in parallel.
  3. Writes a four-item "throughput checkpoint" as todo items. The items are blocking first steps, independent workstreams, shared mutable state, and the smallest safe decomposition. An item that does not apply stays on the list with n/a: <reason>.
  4. Delegates the code to a subagent with a specific scope. The scope names the file paths, the data shape, and the success criteria. When several valid shapes exist, it uses the arena skill instead.
  5. Verifies on the matching surface. A result of "inconclusive" or a check on the wrong surface is not a pass, and the agent flags it.
  6. Rebases the work into small, ordered commits, using the sequence-verifiable-units principle skill.
  7. Runs interrogate before shipping if the design is contested.
  8. Runs the Opening a PR playbook.

What you get back. A reply with what the agent built, what it chose and why, the throughput checkpoint, and the open decisions. Design alternatives appear in tables.

  • Code-coupled work, such as one feature or one migration, goes to a single owner. Parent-level fan-out suits independent artifacts only.

Refactoring

Use it when. You want to change how code is organized, such as a rename, an extract, a move, or a dedupe, without changing what it does.

In plain words. A refactor changes structure and keeps behavior. To prove that, the agent first records what the code does today. This record is a "pin", such as a characterization test (a test that captures current output, right or wrong) or a snapshot. Every later step must keep the pin green. The playbook also removes dead code before it adds anything, and it reverts a change that does not make the code easier to read.

What it does.

  1. Pins the behavior first. It runs how over the subsystem, then writes a characterization test, snapshot, or equivalence harness. Type check and lint are not a pin.
  2. Names the structure the code is missing, per principle-model-the-domain. The reshape must delete branches or invalid states, not add indirection.
  3. Names the target shape. If the target crosses a function boundary, it runs architect.
  4. Subtracts before adding. It deletes dead code, one-caller wrappers, and redundant validators first.
  5. Moves in small steps that each keep the pin green. For API changes it migrates every caller and deletes the old API in the same wave. It spot-checks every rename against the real files and delegates mechanical edits to a subagent.
  6. Proves behavior is unchanged on the real artifact. For larger reshapes it runs an equivalence check, such as a script that diffs old and new output.
  7. Confirms the change lowers reader load. If it does not, the agent reverts it.
  8. Rebases into small ordered commits (subtraction, then reshape, then cleanup) and runs the Opening a PR playbook.

What you get back. The structure that changed, the pin it held against, the equivalence proof, the reader-load change, and what shipped or got reverted. The change adds no new behavior.

Use it when. Your work is done on a branch and you want it turned into a clean pull request that a reviewer can read in about a minute.

In plain words. A PR (pull request) is a request to merge your branch into the main line of code, called trunk. This playbook is the last step of every other playbook, and you can also ask for it alone. It works from a git worktree, which is a separate checkout of the repo, so unrelated work cannot leak in. What it does.

  2. Rebases the work into small, ordered commits. Each commit should be landable and tell part of the story.

Babysit

Use it when. A PR is open and you want it driven to merge-ready, or you want a quick status check on it.

In plain words. A PR collects blockers as soon as it opens. Checks fail, reviewers comment, and trunk (the main branch) moves. CI means the automated checks that run on the PR. Babysit handles those blockers in a fixed order, so the checks restart as few times as possible. It stops at merge-ready, which means the forge (GitHub or Origin) agrees the PR can merge. It never merges.

What it does.

  1. Declares a mode before any poll. drive runs the loop to merge-ready. background triages without blocking. threads-only answers review comments only. check is one status pass and a report. If you give no mode, it uses drive.
  2. Resolves the forge. It uses gh by default, or origin pr when the Origin CLI can resolve the repo.
  3. Works only the merge frontier, which is the lowest unmerged PR in a stack. Upstack threads are read and batched, not fixed.
  4. Handles blockers in this order. Conflicts first, then review threads, then CI. It batches every known fix into one push.
  5. Reads status from scripts/watch-pr/watch-pr on GitHub, or from origin pr view, origin pr thread list, and origin pr checks on Origin. It runs drive and background under /loop.
  6. Classifies each CI failure before any retrigger. A flake earns one fresh build and no more. A failure in code the diff never touched means a stale base.
  7. Triages Bugbot comments skeptically per ../references/bugbot-triage.md. Real findings get a fix with a red-first proof. Noise gets a dismissal with the concrete disproof on the thread.
  8. Stops at merge-ready and reports. It does not merge.

What you get back. A report on the frontier PR. It says whether it is merge-ready or what still blocks it, and names any conflict that needs a rebase by the branch owner. After a drive run it also offers any team-useful dismissal pattern as a candidate entry for the shared Bugbot rubric.

Shipping

Use it when. Your stack of PRs is green and you want it landed safely, one verified PR at a time.

In plain words. Green checks do not prove a change works, because CI does not run the change the way a user would. So Shipping asks a separate verifier agent to run each PR for real before anything merges. A stack is a chain of PRs where each one builds on the one below. Shipping lands only the verified PRs that touch the bottom of the chain, in order, and stops at the first PR that has no passing verdict.

What it does.

  1. Resolves the forge (gh by default, origin pr when available). Then runs one verifier per PR, each a Cursor cloud agent. The verifier uses the matching control skill, such as control-ui or control-cli, and posts PASS, PASS+NOTES, or FAIL on the PR.
  2. Walks up from the lowest unmerged PR and stops at the first one without PASS or PASS+NOTES. The PRs below that point are the run. The top one is the ceiling.
  3. Checks that each verdict still describes the code. It compares git patch-id at the verdict SHA with the current head, because a rebase moves a PR to a new SHA.
  4. Lands bottom-up, one PR at a time, with origin pr merge <pr> or gh pr merge <pr> --squash. It reads the PR back to confirm the merge, then retargets the next PR to trunk and pushes with --force-with-lease.
  5. Leaves the stack alone while it lands. On GitHub it watches with scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top> under /loop until COMPLETE.
  6. Stops at the ceiling. Extending the run needs new verdicts.

What you get back. The verified run and its ceiling. For each PR, its verdict and who produced it. What landed and how the merge was confirmed. What the next gap needs.

Autopilot Full

Use it when. You have a queue of independent changes, you grant full autonomy, and you want each one built, verified, and merged.

In plain words. Autopilot-full gives each PR its own owner agent. The owner builds the change, opens the PR, proves it, babysits it to green, and merges it. The twist is that no owner merges on its own say-so. A separate swarm, which is a group of verifier agents that did not write the code, must prove the code that lands. Green CI alone never authorizes a merge, because CI covers one head and a verdict covers one patch.

What it does.

  1. Honors the operator's gates first. Items you name as yours and PRs outside the queue stop at merge-ready. A request to state the plan is not a go.
  2. Spawns one owner per PR. Each is a Cursor cloud agent that builds, opens its PR per playbooks/opening-a-pr.md, proves the change on the real artifact, and babysits per playbooks/babysit.md. The code counts as ready only after the /deslop and /no-comments passes. Each owner then rebases onto trunk and reports a code-ready head. They keep a decision trail per the show-me-your-work skill.

Autonomous run

Use it when. You have one long task and you want the agent to keep working until a clear finish line is met, without checking in.

In plain words. The agent first writes down what "done" means as a check it can run, such as "all tests pass". This check is called the exit condition, or predicate. Then it loops. Each round it makes the smallest change that the evidence supports, tests it against the check, and keeps it only if it helped. The agent handles side problems itself and stops only when the check passes or it hits a real dead end.

What it does.

  1. Write the exit condition as a checkable predicate before the first iteration.
  2. Pick a wake mechanism with Cursor's /loop command. Use a watcher subagent if there is an event to watch (CI, a merge). Use a fixed-interval heartbeat if there is not.
  3. Make the smallest change the evidence justifies, verify it against the predicate, and commit it if it advanced. Discard changes that did not help. The sequence-verifiable-units skill orders the work so each unit is checked before the next.
  4. Fix mid-run discoveries yourself through poteto-mode, such as flaky verifiers or related bugs. Put out-of-band fixes in their own PR. Surface only irreversible actions, product calls no experiment can settle, or a real dead end.
  5. Checkpoint every iteration with the show-me-your-work skill. Add a row for what changed and whether the predicate moved.
  6. Stop when the predicate is met. A plateau is not a stop, so change approach. Never relax the predicate to declare victory.

What you get back. A reply with the exit condition, the number of iterations run, what landed, what was discarded, and the final state of the predicate.

Orchestrate

Use it when. You hand over a whole project that runs for days, with many stacked PRs and dozens of subagents, and you want to check in only a couple of times a day.

In plain words. One standing chat acts as the coordinator. The coordinator never writes code. It writes briefs, collects results, keeps the merge line green, and makes decisions. Workers are subagents, which are helper agents that each do one unit of work. A worker cannot ask the coordinator questions, so every brief must be complete. The playbook warns that a vague brief fails quietly. Use this only when the work outlives one agent. A task one agent can finish in the session is Autonomous run instead.

What it does.

  1. Frame the project. State a countable done predicate, such as "all 126 units merged". Quantify units, effort, and time budget. If one agent could finish in that budget, stop and run Autonomous run.
  2. Install the runtime. Run orch init, open the trail with the show-me-your-work skill, write the standing orders (preferences.md) before any spawn, and seed frontier.json with orch frontier set --repo <repo-dir>.
  3. Pilot one unit through the full path (brief, worker, verification, stack entry, ledger row, merge). Fix the contract from that evidence before any fan-out.
  4. Scale with a rolling window of workers. Refill as children finish. Spawn track sub-coordinators only if one coordinator cannot drain the program.
  5. Drain the queue at set points. Completions are queue events. Run orch inbox drain, classify each pointer, write the rows, run orch status, and spawn the next wave.
  6. Land continuously and keep the frontier green. One stacker per stack changes topology. Workers never rebase, retarget, or merge.
  7. Verify with ledger rows keyed by PR and head SHA. Use a verifier on a different model family when verification is costly.
  8. Close. Reconcile every spawned agent to a terminal row, confirm the predicate on the real artifact, and keep the store as the postmortem.

What you get back. A reply at checkpoints and at close with the predicate and the count against it, what each track landed, the frontier (PR list plus SHAs), a verdict summary, what was abandoned and why, the gates awaiting you, the store path, the trail path, and PR links. Numbers come from units.tsv and ledger.tsv.

Session pickup

Use it when. An earlier agent started work, and you want a fresh agent to take over from where it stopped.

In plain words. The playbook treats the earlier agent's trail as the source of truth. A trail is a transcript, a cloud-agent URL, or a pushed branch. The new agent reads it, works out what already landed and what is left, and continues from there. It does not redo finished work. It does check the final result on the real artifact, because a past "it passed" is a report and not proof.

What it does.

  1. Locate the prior trail in the active workspace's agent-transcripts/ directory, a cloud-agent URL, or a pushed branch. Read the overview and last messages first. Parse a long transcript in a subagent.

  5. Verify the inherited claims against the original goal on the real artifact, using the principle-prove-it-works skill.

Pause safely

Use it when. You must stop work now and want the agent to leave a clean checkpoint that a fresh agent can resume from.

In plain words. A pause is a stop that loses nothing. The agent finishes or backs out of its current step, saves its edits in one commit, and writes a resume note. The note says what the work is for, how far it got, and what to do first. Compaction is when a long chat is trimmed to fit its memory. A resume note on disk survives compaction. This playbook runs only when you ask for it.

What it does.

  1. Stop at a safe boundary. Finish the current atomic step or back out of it. Start nothing new and cancel any nested subagents.
  2. Take no irreversible action to pause. Make no PR and no push unless one was already out.
  3. Make the work durable. Commit uncommitted edits as one clear wip: commit on the current branch. If the tree is broken, say so in the commit body in one line.
  4. Write the resume note off-context. Include intent, what you were doing, progress and what is verified, current state, next steps, key files, and gotchas. For the compaction trigger, write it to a file such as /tmp/<slug>-resume.md. If a show-me-your-work trail exists, point at it instead of copying it.

What you get back. A reply with where you are in the loop, what is on disk versus still in the agent's head (paths, no diff dumps), the commits made and whether the tree is clean, and the first action on resume. It is a pause, not a final report.

Worktree and simulator cleanup

Use it when. Your disk is filling up and you want to remove old git worktrees and stale iOS simulators safely.

In plain words. A git worktree is an extra checked-out copy of a repository, often made for a branch or a task. They pile up and take disk space. This playbook runs an audit script that lists each worktree with its size, age, and state, and suggests a bucket for it. The bucket is advice only. The agent then confirms which chats still use each worktree before it deletes anything. This playbook deletes user state with no code review to catch a slip, so its gates act as the review.

What it does.

  1. Record df -h /. Run scripts/worktree-audit.sh [-b <pr-base-ref>] [repo-path]. Pass -b origin/<branch> when PRs target another branch. Run the slow transcript scan in the background.
  2. Treat the bucket as advice. Get the pinned and active chats from you or the sidebar, and cross-check every candidate. The pinned set wins.
  3. Verify usage before deleting. For each verify-recent-chat row, or anything doubtful, fan out subagents to read the transcripts.
  4. Pause on irreversible loss. wip:N is N tracked uncommitted edits, so show the diff and get a decision first. scratch:N is untracked throwaway, safe to drop, but name the files.
  5. Prune the confirmed set with git worktree remove --force <path>. If the directory survives, rm -rf it, then run git worktree prune. Branch refs survive. Confirm with df -h / and re-list.
  6. Reclaim simulators and other caches. The playbook lists xcrun simctl --set testing delete all, xcrun simctl delete unavailable, xcrun simctl runtime list then runtime delete <id>, Xcode DerivedData and iOS DeviceSupport, Cursor application support files, and package caches. Clear only caches you have not said to keep.

What you get back. A reply with df -h / before and after and the space reclaimed, the worktrees pruned, and a one-line reason for each one held back (in use by which chat, or uncommitted work).
